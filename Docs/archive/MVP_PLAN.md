# ArtFlex 第一阶段 MVP 开发计划

## 目标

ArtFlex 是旧版 `BrushCanvas` 的 Metal 重构版。

第一阶段的目标不是一次性复刻旧项目全部功能，而是先建立一个可长期演进的最小可用核心版本：

- 保留旧项目已经验证过的主界面结构和主工作流
- 以 Metal-first 方式重建画布与渲染底层
- 避免继续沿用旧项目 CPU / `CGContext` / `CGImage` 的核心方案
- 先打通一条可编译、可运行、可验证的最小闭环

第一阶段的核心闭环应为：

`文档真相源 -> Metal 显示 -> 画笔写入 -> PNG 导出 -> 工程保存`

---

## 第一阶段必须实现的最小功能

### 1. App 壳层

- macOS 应用可启动
- 主窗口可正常打开
- 基础菜单和文件入口可挂接

### 2. 主窗口结构

保留旧项目已经验证过的桌面绘图软件布局：

- 顶部工具栏
- 左侧竖向工具栏
- 中央视图画布
- 右侧参数区
- 图层面板区域
- 为笔尖形状设计区域预留位置

第一阶段允许部分右侧区域先以占位面板实现，但整体布局不要随意改动。

### 3. Metal 画布

- 中央区域使用 Metal 画布显示
- 显示深色工作区背景
- 显示白色可绘制画布区域
- 支持窗口 resize 后稳定显示

### 4. 单图层文档

- 支持一个最小文档对象
- 支持一个基础图层
- 图层像素数据作为当前阶段唯一绘制目标

### 5. 基础画笔

- 可在画布上连续绘制
- 至少支持大小和透明度两个参数
- 使用统一的底层画布真相源写入

### 6. 橡皮擦

- 可擦除当前图层内容
- 尽量复用与画笔相同的笔划执行链

### 7. 视图控制

- 平移
- 缩放
- 重置视角

### 8. 基础颜色选择

- 当前颜色可调整
- 当前颜色可用于画笔绘制

### 9. PNG 导出

- 可将当前文档导出为 PNG
- 导出必须来自与显示一致的统一真相源

### 10. 最小工程保存格式

- 可保存当前阶段需要的文档信息
- 可重新打开并恢复最小文档状态

---

## 第一阶段暂不实现的旧项目功能

以下功能明确延后，避免第一阶段范围膨胀：

- 多图层
- 图层排序 / 合并 / 锁定 / 透明度 / 可见性
- 撤销 / 重做
- 吸管
- 油漆桶
- 涂抹
- 套索选区
- 矩形选区
- 椭圆选区
- 套索填充 / 套索擦除
- 自由变形
- 笔刷库
- 自定义笔尖完整设计系统
- 生成器系统
- 复制 / 剪切 / 粘贴
- JPEG 导出
- 旧项目工程格式兼容
- 高级笔刷参数，如散布、旋转、抖动、压感曲线等

这些能力都很重要，但大多会引入新的底层状态、取样路径、缓存策略或复杂文档模型，不适合在第一阶段与基础渲染链路同时推进。

## 推荐的项目目录结构

建议从一开始按职责拆分，避免未来再次演变成巨型状态对象或 UI/渲染耦合结构。

```text
ArtFlex/
  App/
    Bootstrap/

  Platform/
    macOS/
      App/
      UI/
      Canvas/
      Services/

  Core/
    Document/
    Layer/
    Tools/
    Viewport/
    Color/
    Application/

  Rendering/
    Metal/
    Canvas/
    Shaders/

  Infrastructure/
    FileFormat/

  Tests/
    CoreTests/
    RenderingTests/
    IntegrationTests/
```

### 各层职责

#### `Platform/macOS`

负责：

- SwiftUI / AppKit 窗口与视图
- 菜单
- 文件面板
- 平台输入事件接入
- Metal 视图宿主

不负责：

- 文档真相源定义
- 图层像素管理
- 业务规则

#### `Core`

负责：

- 文档模型
- 图层模型
- 工具状态
- 视口状态
- 应用控制逻辑

要求：

- 尽量不直接依赖 SwiftUI / AppKit
- 不把所有状态重新塞进一个巨型 `CanvasState`

#### `Rendering`

负责：

- Metal 设备和命令调度
- 图层 surface 管理
- 画布合成
- 画笔和橡皮擦执行
- 读回导出所需图像数据

要求：

- 尽量与上层逻辑分离
- 不反向依赖平台窗口或界面代码

#### `Infrastructure`

负责：

- 工程文件格式
- PNG 导出
- 持久化相关辅助逻辑

## UI 层、状态层、Metal 渲染层的分离方式

## 1. UI 层

UI 层只负责：

- 展示主界面结构
- 显示当前文档和工具状态
- 接收鼠标、键盘、手势输入
- 把输入转成应用层命令

UI 层不负责：

- 直接保存图层位图
- 直接操作 Metal texture
- 定义导出或工程格式

## 2. 状态层

状态层建议拆分为三类，而不是聚合成一个大对象：

### `Document State`

负责：

- 画布尺寸
- 图层列表
- 当前活动图层
- 文档元数据

第一阶段里可以只有一个图层，但结构上仍建议单独建模。

### `Session State`

负责：

- 当前工具
- 当前颜色
- 画笔参数
- 当前绘制会话中的临时状态

### `Viewport State`

负责：

- 缩放
- 平移
- 画布坐标与屏幕坐标变换

## 3. Metal 渲染层

渲染层负责：

- 管理图层对应的 GPU surface
- 将文档内容显示到屏幕
- 执行画笔和橡皮擦写入
- 从统一真相源读回用于导出

第一阶段建议坚持以下原则：

- 单图层对应单个标准化底层 surface
- 屏幕显示从该 surface 来
- PNG 导出从该 surface 来
- 后续吸管和涂抹也应以同一真相源为基础，而不是另建旁路

## 第一阶段建议的开发步骤

每一步都应满足：

- 可以编译
- 可以运行
- 可以验证

### 第 1 步：先定义颜色与像素规范

必须先明确并固定：

- CPU 侧像素格式
- Metal texture format
- render target pixel format
- premultiplied alpha 规则
- sRGB / linear 规则
- 导出读取的数据源
- 后续吸管 / 涂抹计划读取的数据源

这是第一阶段最先做的事情，不应边做边改。

### 第 2 步：建立 Core 最小模型

建立最小必需的数据结构：

- 文档模型
- 单图层模型
- 工具类型
- 画笔基础参数
- 视口模型

这一层应尽量不依赖 SwiftUI / AppKit。

### 第 3 步：搭出主窗口骨架

完成：

- 顶部工具栏区域
- 左侧工具栏区域
- 中央视图画布区域
- 右侧面板区域

这一阶段允许面板内容先是占位视图，但布局结构应固定下来。

### 第 4 步：打通 Metal 最小显示链路

完成：

- Metal 视图创建
- 基础 render loop 或按需刷新链路
- 深色工作区背景显示
- 白色画布区域显示

此时先不接笔刷。

### 第 5 步：建立单图层 surface 与显示绑定

完成：

- 文档中的单图层映射到一个底层 GPU surface
- 画布从该 surface 稳定显示

目标是明确“真实数据在哪”和“显示从哪来”。

### 第 6 步：实现视口系统

完成：

- 平移
- 缩放
- 重置视角

同时验证：

- 屏幕坐标到画布坐标的转换
- resize 后视图变换是否稳定

### 第 7 步：实现基础画笔

建议先做最小可用版本：

- 圆形 stamp
- 连续插值
- 基础大小
- 基础透明度

此阶段优先跑通写入链路，不追求复杂笔刷质感。

### 第 8 步：实现橡皮擦

要求：

- 尽量与画笔共用一条笔划执行路径
- 通过不同写入或混合策略实现擦除

这样可以减少未来架构分叉。

### 第 9 步：接入最小参数 UI

完成：

- 颜色选择
- 画笔 / 橡皮切换
- 大小调节
- 透明度调节

只接 MVP 必须项，不提前扩展完整参数系统。

### 第 10 步：实现 PNG 导出

要求：

- 从统一真相源导出
- 与屏幕显示结果保持一致
- 不新增一条 CPU 临时重绘导出路径

### 第 11 步：实现最小工程保存格式

建议保存内容包括：

- 画布尺寸
- 单图层像素数据
- 当前阶段需要的工具参数
- 文档元数据

目标是先形成最小恢复能力，不追求复杂兼容性。

---

## 哪一步最先做，为什么

第一步必须是：

**颜色与像素规范定义。**

原因：

- 它决定文档真相源的格式
- 它决定纹理格式和混合规则
- 它决定显示、编辑、导出是否能共享同一条链路
- 它能从一开始避免通道交换、颜色补偿、shader 临时修正这类补丁式问题

如果这一步不先做，后面的画笔、导出、取样都容易走向分裂路径，后续再修会非常昂贵。

---

## 第一阶段的总体决策

第一阶段不追求功能数量，而追求结构正确：

- 产品结构先对齐旧项目
- 底层实现彻底转向 Metal-first
- 核心模型和应用逻辑不绑死在 macOS UI 层
- 先做最小闭环，再逐步追平旧功能

换句话说，第一阶段真正要交付的，不只是“能画几笔”，而是一个能继续长下去的基础版本。
