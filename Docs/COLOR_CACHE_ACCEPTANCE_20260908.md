# 调色缓存生命周期与回归隔离（2026-09-08）

## 决策与范围

承接磁盘撤销回归中偶发失败的两项 `QuickColorPickerHUDTests`。复用 `ColorPickerDisplayImageCache`、原生 `NSCache`、现有后台图片生成和 SwiftUI `.task(id:)`；不引入依赖、不自建生产缓存、不改变颜色公式或快捷键。

参考 [Apple NSCache](https://developer.apple.com/documentation/foundation/nscache) 与 [Swift Testing 并行执行](https://developer.apple.com/documentation/testing/parallelization)。主页面的 Markdown 正文已读取。NSCache 是可被系统淘汰的临时优化；不能要求它像持久字典一样保证保留。Swift Testing 默认同进程并行，使用共享缓存并清空会扩大用例间干扰。

执行顺序是先隔离缓存依赖，再覆盖命中、淘汰与取消，最后全量及界面验证。无需更换底层缓存或禁用并行测试。

## 可确认与不能确认

- 原测试直接清空 `.shared`，并要求缓存命中次数固定、异步预热后缓存一定非空。
- 第一次全量曾观察到 buildCount 3（预期 2），预热后缓存 nil；定向复测及下一轮全量通过。现有日志没有记录当时的缓存淘汰来源，不能断言那一次一定是内存压力或某个并行任务。
- 返回图片与缓存是否仍持有图片是两回事。新用例使每次写缓存立即被淘汰，仍要求返回图片存在且像素正确；这直接检验产品需要的恢复行为。
- 另外确认快捷调色窗的旧 `.task` 被取消后，原来仍会把返回值赋给 `displayImage`。取消的生成任务会返回 nil，因此旧任务可能清空已有显示。消费端现已在赋值前检查取消；没有以此推断上述两次缓存断言的根因。
